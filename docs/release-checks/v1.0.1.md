# llamavm v1.0.1 release checks

Hotfix for v1.0.0. Issue: installs from v1.0.0 produced binaries that
couldn't load their dylibs after the staging→final dir promotion. Root
cause was twofold; v1.0.1 addresses both.

## Bug summary

`llamavm install <tag>` builds llama.cpp inside `~/.llamavm/versions/.staging-<tag>/source/build/`,
then renames the staging dir to `~/.llamavm/versions/<tag>/`. Two artifacts
of the build baked the staging-dir absolute path in:

1. The `bin/llama-cli` symlinks pointed at the staging path's
   `source/build/bin/llama-cli` via absolute targets.
2. The Mach-O binaries themselves carried `LC_RPATH = <abs-staging>/source/build/bin`.
   `CMAKE_BUILD_RPATH_USE_ORIGIN=ON` is set in our cmake configure args
   but llama.cpp's CMakeLists pin LC_RPATH to the build dir explicitly,
   overriding the cmake hint.

After the rename, both pointed at `<abs>/.staging-<tag>/...` which no
longer existed. `llama-cli` failed at dyld load with "Library not loaded:
@rpath/libllama-common.0.dylib".

## Fix

Two commits land in v1.0.1:

- `437f042` switches bin/ symlinks to relative targets (`../source/build/bin/<name>`)
  and adds the cmake rpath flag (kept for defense-in-depth even though it
  proved insufficient against llama.cpp's own settings).
- `2c3069b` adds a post-build `install_name_tool` pass in `runInstall` that
  rewrites every Mach-O LC_RPATH pointing at the build dir to `@loader_path`.
  Symlinks (cmake's libfoo.dylib → libfoo.0.dylib → libfoo.0.10.2.dylib
  chain) are skipped to avoid double-add failures.

Existing v1.0.0 installs need to be reinstalled:

```bash
llamavm uninstall <tag>
llamavm install <tag>
```
